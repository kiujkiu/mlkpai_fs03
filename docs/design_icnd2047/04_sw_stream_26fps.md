# 04 — PC→WiFi→板端推流 26 页/秒软件升级方案

[2026-07-13] 状态: 设计稿 (待 S0 板端实测校准)
适用: FS03 新一代双屏 POV — 转速 13 rps × 双屏对置 = **26 页/秒** 体积刷新
基线代码: `stream/protocol.h` (PVS1) / `stream/pc/povstream.py` / `stream/board/pov_rxd.c`

---

## 0. 目标与现状基线

| 项 | 现状 (单屏 4.5 rps) | 新目标 (双屏 13 rps) |
|---|---|---|
| 页率 (翻页/秒) | 4.5 | **26** (每半圈翻一页) |
| 每页预算 | 222 ms | **38.5 ms** |
| 帧 raw | 4,423,680 B (360×0x3000) | 不变 (双屏共用同一份) |
| 帧 zlib-6 后 | 80–130 KB (角色类实测) | 不变 |
| 需求带宽 | 4.5×(80–130KB)×8 ≈ 2.9–4.7 Mbps | **16.6–27.0 Mbps** |
| 链路 (2.4G ch6 实测) | 28 Mbps, 占 12% | 占 **59–96%, 顶格贴脸** |
| 翻页节拍 | 每圈 1 次 (slice wrap≈0) | **每半圈 1 次** (slice≈0 和 ≈180) |

两个独立瓶颈, 都必须解:
1. **链路带宽**: 2.4G 28 Mbps 对 27 Mbps 峰值无余量 (WiFi 半双工 + ACK RTT + 邻道干扰, 实际可持续 ≈ 70% 标称)。
2. **板端 CPU** (更硬): pov_rxd 现串行路径估算 130–230 ms/帧 (见 §3.1), 超预算 3–6×。带宽解了板端不解照样卡 13 页以下。

## 1. 带宽方案对比

### ① 5G WiFi (mt7921u dongle, 首选)

已有实测底子 (memory 2026-06-29): 连 AP `undef` 5GHz/ch161(5805), 信号 -48 dBm, tx bitrate **172 Mbps**; LAN 双跳 wget 实测 **9.43 MB/s ≈ 75 Mbps** (PC+板都走 WiFi = 共享 AP 减半) → **PC 插网线单跳估 ≈150 Mbps**。

- 26 fps 需 17–27 Mbps → 5G 单跳占用 **11–18%**, 余量 5 倍, 是唯一"舒服"的无线方案。
- **欠账 1 — 锁频不生效**: wpa_supplicant `freq_list` 曾不生效, dongle 仍落 2.4G。修法按序试:
  1. network 块内写 `freq_list=5805 5745 5785` (注意要在 `network={}` 内, 全局位置无效);
  2. `bssid=<5G BSSID>` 硬钉 (iw scan 抄 5G 那个 BSSID, 最可靠);
  3. `scan_freq=5805` 减少漫游回 2.4G;
  4. 终极: 让 AP 拆出独立 5G SSID (办公 AP 双频同名是漫游回 2.4G 的根因)。
- **欠账 2 — 供电 brownout**: 5G 持续 30 Mbps 负载功耗高于当时 wget 测试, 板靠 PC Type-C 供电边缘 (前科: 连 WiFi 两次掉电)。**必须上带供电 USB Hub 或独立 5V**, 联调纳入 S2 验收 (60s iperf 0 掉电)。
- 成本: 纯配置, **0 行代码**。

### ② 帧间 delta 编码 (XOR + zlib)

发送 `cur XOR prev` 再 zlib。1-bit 数据帧间变化率实测 ~35%。

- 压缩比估算: 点亮体素 35% 挪位 → XOR 帧点密度 ≈ 0.7× 原帧 (旧位+新位都置 1), 但 65% 静止区域全零化, zlib 后估 **0.45–0.6× 关键帧大小 ≈ 40–75 KB/帧** → 26 fps ≈ **8.3–15.6 Mbps**, 整体增益 ~1.7–2.2×。
- ⚠️ **时域抖动是 delta 的天敌**: povstream 现在 Bayer 相位逐帧变 (`phase = slot + frame_idx*7`), 静止内容也逐帧变字节 → 35% 变化率里有一块是抖动自己贡献的。delta 模式下把抖动相位冻结 (只随 slot 变不随 frame 变), 慢动画的 delta 可望压到 0.3× 以下; 代价是丢失时域抖动的灰度平滑 → 做成开关, S5 实测取舍。
- 关键帧: TCP 无丢包, 参考帧 = 流序上一帧 (与板端"丢帧不翻页"无关, 解码顺序不受影响), 严格说只需连接建立/重连时发关键帧; 保险起见周期 K=52 (2 秒) 一个, 平摊带宽 +≈1 KB/帧, 可忽略。
- 附带收益: XOR 应用在板端仅 ~8–15 ms (NEON, cached), 解压输入变小 inflate 也稍快。
- 成本: 协议 +1 个 flag 位 (§2), PC 端在预渲染时预计算 (0 实时开销), 板端 +1 份 4.4 MB cached 参考帧 + XOR 循环, 约 60 行 C。

### ③ 降片 360→180

角度分辨率减半: 外缘 (r=80px) 切片间距 1.4px → 2.8px, 边缘可见变粗, 内圈内容基本无感。分两档:

- **③a PC-only 版 (0 协议/板端改动)**: `--render-slices 180` 本来就把每个渲染角复制进 2 个槽; 只要把复制槽的抖动相位统一 (现在 `phase = slot + ...` 逐槽变导致复制槽字节不同, 改成 `phase = (slot//dup)*dup + frame_idx*7` 一行), 相邻重复 slice (stride 12 KB < zlib 32 KB 窗口) 被 zlib 后向引用吃掉 → 线上体积估 **0.55× ≈ 44–72 KB → 9.2–15 Mbps**。板端 inflate 输出仍 4.4 MB (CPU 不省, 但重复段走 match-copy 快路径)。
- **③b 协议版 (n_slices=180 上线)**: raw 减半 2.2 MB, 板端 inflate 输出/拷贝 **CPU 也减半**, 板端按槽复制或 PL 直接配 180 片。改协议+板端, 留作 CPU 账不够时的后手。

### ④ 有线兜底 (GbE)

FS03 板 GEM0 + YT8531 千兆 PHY 现成 (Zynq 是基座静止侧, 物理无障碍)。A9 上 GEM 实际 300–600 Mbps, 对 27 Mbps 需求 10–20 倍余量, 甚至 zlib-1 (476 KB/帧, 99 Mbps) 都随便跑。

- 定位: **联调基准链路** (把"带宽变量"清零, 单独暴露板端 CPU 问题) + 演示现场 WiFi 环境失控时的兜底。
- 成本: 一根网线 + 板端 `ip addr` 静态配置, 0 代码 (pov_rxd 本来就不关心接口)。

### 推荐组合与实施顺序

| 序 | 方案 | 角色 | 代码量 |
|---|---|---|---|
| 1 | ④ 有线 GbE | 先当联调基准, 隔离带宽变量 | 0 |
| 2 | ① 5G 锁频 + 供电 | **主力生产链路** (占用 11–18%) | 0 (纯配置) |
| 3 | ③a 180 片 PC-only | 免费旋钮, 按内容取舍画质 | ~5 行 Python |
| 4 | ② delta | 2.4G 应急运行能力 + 5G 余量翻倍的保险 | 协议 +1 bit, PC/板各小改 |
| 5 | ③b 180 片协议版 | 仅当 S0 实测板端 inflate 超 38 ms 才做 | 中 |

结论: **带宽主路 = 5G 锁频 (0 代码), delta 做协议级保险, 2.4G 只作 delta+180 片下的降级模式, 有线保联调/演示底**。不要在 2.4G 上硬凑 26 fps——59–96% 占用没有工程余量。

## 2. 协议演进 (PVS1 → PVS1.1)

### 2.1 结论先行: 数据共用 → 协议骨架不动

双屏对置显示**同一份 360 片体积帧**: 屏 B 在角度 θ+180° 处取 slice `(idx+180)%360`, 这是 **PL 取数地址偏移问题 (板端寄存器/PL 配置), 不是数据流问题**。协议传的是"角度→图案"的完整映射, 两个屏只是同一映射的两个读出头。因此:

- **双屏相位字段: 不进协议。** 相位属于显示器硬件拓扑 (装了几个屏、各在几度), 传输层不该知道。若未来两屏显示不同内容 (不共用帧) 才需要升协议 —— 那是 PVS2 的事, 现在不预支。
- **关键帧周期: 不进协议。** 它是发送端策略 (发几个 delta 插一个全帧), 接收端只需按 flag 逐帧处理, 无需知道周期。
- magic 保持 `PVS1`, 头 16 B 布局不变, n_slices=360 不变。

### 2.2 唯一改动: flags 加 1 位

```c
#define PVS_FLAG_DELTA   (1u << 2)  /* payload 解压后 = cur XOR prev_raw */
```

- 语义: 与 `PVS_FLAG_ZLIB` 组合使用 (`flags = ZLIB|DELTA`); 解压得 4,423,680 B XOR 帧, 与"本连接内上一帧解码结果"异或得本帧。`raw_len`/`n_slices` 校验不变。
- 接收端规则: 连接建立后第一帧带 DELTA → **NAK** (无参考帧); 发送端收 NAK 本来就 abort, 改为"降级重发关键帧"(见 2.3)。
- **向后兼容天然成立**: 旧 pov_rxd 对未知 flags 直接 NAK (`h.flags != 0 && != RLE && != ZLIB`), 新 PC 端收到首帧 NAK 即可判定"旧板端", 自动全程发全帧。旧 PC 打新板也不受影响。
- 顺带修一个现存小 bug: 板端 flags 校验是 `!=` 精确匹配, 新板端改成"已知位掩码"校验 (`flags & ~(RLE|ZLIB|DELTA)` 非零才 NAK), 给未来留位。

### 2.3 NAK 语义微调 (发送端)

现 NAK = sender abort。改为: **NAK 且当前帧是 delta → 立即重发对应关键帧后继续; NAK 且当前帧是全帧 → abort (维持原语义)**。板端重启/重连后参考帧丢失的恢复就是自动的。

## 3. 板端 pov_rxd 改动清单

### 3.1 26 页/秒 CPU 账 (Cortex-A9 单核 667 MHz, 每帧预算 38.5 ms)

现串行路径逐项估算 (⚠️ 数量级估算, S0 上板实测校准):

| 阶段 | 现状估算 | 依据 | 改后目标 |
|---|---|---|---|
| TCP recv 110 KB | 31 ms @2.4G / 6 ms @5G | stop-and-wait 下线时间不与计算重叠 | 流水化后隐藏 (独立阶段) |
| zlib inflate 130KB→4.4MB | **30–90 ms** | x86 实测 7 ms (≈630 MB/s); A9 inflate 一般 40–80 MB/s, 本数据 94% 零 (长 match-copy 快路径) 乐观 100–150 MB/s | ≤ 30 ms (zlib-ng/NEON ×1.5–2), 或 ③b 减半, 或双核双帧交替 |
| memcpy staging→bank 4.4MB | **37–73 ms** 🔴 | `/dev/mem` 于 `!pfn_valid` 区域拿到的是 **pgprot_noncached = Strongly-Ordered**, 每个 store 不可缓冲, 实效 ~60–120 MB/s | **WC 映射后 6–15 ms** (§3.3) |
| crc32 4.4MB | 11–18 ms | zlib crc32 A9 ~250–400 MB/s | **删掉** (改 `--check` 调试选项) |
| flip 等待 wrap | 平均 ~19 ms (半圈) | 忙等占核 | 移到独立线程, 0 占用 |
| **合计 (串行)** | **≈130–230 ms/帧 → 4–7 fps** | 与实测 4.5 rps 吻合 ✓ | 流水后最长单阶段 ≤ 38.5 ms |

**结论: 板端最大风险 = inflate + Strongly-Ordered 拷贝这两项 CPU 大头**, 带宽全解了它也只能跑 4–7 fps。两项都有明确解法, 但 inflate 实测数字 (S0) 决定要不要动用 ③b/双核解码/换 zstd 三个后手。

DDR 带宽旁证: 26 fps 下 inflate 写 115 MB/s + 拷贝读写 230 MB/s + PL 取片读 115 MB/s ≈ 460 MB/s, 对 16-bit DDR3L-1066 (~2.1 GB/s 理论 / ~1.2 GB/s 实效) 占 ~40%, 可行但别再加大头。

### 3.2 翻页节拍: 每圈 1 次 → 每半圈 1 次

- 13 rps 下 slice 周期 = 1/(13×360) ≈ 214 µs; 现 `SLICE_WRAP_THRESH=8` 窗口 = 1.7 ms, 200 µs 轮询粒度仍够用, 不用改轮询机制。
- `flip_when_wrapped` 的触发条件从 `slice < 8` 改为 **`slice ∈ [0,8) ∪ [180,188)`**, 且记录上次触发窗口防止同窗口双触发。
- 正确性论证: PL `slice_base` 在每片 fetch_go 逐片锁存 → 在 180 边界翻页后, 片 180–359 取新帧; 屏 B 同期取 `(idx+180)%360 = 0–179` 也是新帧 → **每半圈两屏合扫出一个完整、同帧的体积**, 无角度撕裂。前提 (对 PL 的接口假设, 记入 FPGA 侧需求): 双屏第二读头 = 同一 slice_base 加 180 片偏移取数。
- `FLIP_TIMEOUT_MS=2000` 保留 (引擎停转时照翻), 但日志降频 (见 3.5)。

### 3.3 双缓冲 → 三缓冲 + 双线程流水 (要, 且是必改)

**为什么双缓冲不够**: 不是内存问题, 是**节拍耦合**问题。现在 ACK 在翻页之后发出 → 发送端下一帧最早在翻页后才开始上线, "线时间 + 解压"必须塞进下一个 38.5 ms 窗口 (2.4G 线 31 ms + 解压 30 ms = 63 ms), 每两个窗口丢一个 → 封顶 13 fps。**ACK 必须与翻页解耦**, 解耦后同时存在"正在显示 / 已解好待翻 / 正在解压写入"三个帧 → **3 个 bank**。

- Bank 布局: `0x10000000 / 0x10500000 / 0x10A00000` (各 0x438000, 步距维持 0x500000), 顶到 0x10EB8000, 距 256 MB 保留区上限还剩 ~241 MB, 富余。若 S0 后决定双核双帧并行解码, 加第 4 个 bank @ `0x10F00000`。
- 线程划分:
  - **RX/解码线程**: recv 头+payload → inflate (→ 若 DELTA 再 XOR 参考帧) → 写入空闲 bank → 标记 `latest_ready` (原子交换, 旧 ready 未消费则直接顶替 = 天然丢帧策略) → **立即 ACK**。ACK 节拍 = 解码吞吐, 发送端 `--fps 26` 自然贴住。
  - **翻页线程**: 轮询 slice 计数, 每过 0/180 窗口, 若有新 `latest_ready` 则写 `REG_SLICE_BASE` 翻页并归还旧显示 bank。
  - 显示永不阻塞原则不变: 没新帧就重扫旧帧。
- 参考帧 (delta 用) 保存在 **cached malloc 内存** (staging 本身), 不从 uncached bank 读回 (SO 读更慢)。

### 3.4 uncached 拷贝提速: Strongly-Ordered → Write-Combine (必改, 收益最大最确定)

内核 6.6 自编在手 (memory: mlkpai-kernel 流程全通), 三选一, 推荐 a:

- **a. 30 行 misc 驱动 `povmem.ko`**: mmap 帧区并 `vma->vm_page_prot = pgprot_writecombine(...)`, pov_rxd 打开 `/dev/povmem` 替代 `/dev/mem` 映射帧区 (寄存器区继续走 /dev/mem, 寄存器就该 SO)。Normal-NC/WC 写可缓冲合并, memcpy 实效 300–800 MB/s → **4.4 MB ≈ 6–15 ms**。
- b. UIO 平台设备 + dts 注册帧区 (更"正规", 改 DT 麻烦一点)。
- c. inflate 直接以 WC bank 为输出 (省一次拷贝; 但 inflate 有回读窗口的 match copy, 从 WC 读慢, **不推荐**, 保留 staging→bank 单向大拷贝的干净模型)。
- 一致性: WC 是弱序, 翻页前 `__sync_synchronize()`(DMB) 语义保留, 另在写完帧后加 DSB 确保排空 write buffer 再让翻页线程可见 —— 现有代码位置不动, 屏障语义正好覆盖。

### 3.5 改动清单汇总 (按次序)

1. **[必改] 三缓冲 + RX/翻页双线程, ACK 移到解码完成后** (§3.3) —— 解节拍耦合, 没它封顶 13 fps。
2. **[必改] povmem WC 映射** (§3.4) —— 拷贝 37–73 ms → 6–15 ms。
3. **[必改] 半圈翻页双窗口** (§3.2)。
4. **[必改] crc32 移到 `--check` 选项后** (省 11–18 ms; 联调期开着, 量产关)。
5. **[必改] 日志降频**: 26 fps 下每帧 printf 走串口/文件是可观开销, 改每秒一行统计 (fps / 解码 ms / 丢帧数 / 错过翻页窗口数)。
6. [协议] DELTA flag 支持: cached 参考帧 + NEON XOR (~8–15 ms) + 首帧 delta NAK (§2)。
7. [后手, S0 定夺] inflate 提速三选一: 静态链 zlib-ng (×1.5–2) / 换 zstd (板 buster 有 libzstd, 比 zlib 解压快 ~2×且比率更好, 但要动协议 flag) / ③b 180 片减半输出。
8. [后手] 双核: RX/解码线程与翻页线程 `pthread_setaffinity` 分核; mt7921u USB 中断 (26 fps × ~30 Mbps 的 USB2 中断负载不可忽视) 用 `/proc/irq/*/smp_affinity` 钉到翻页核, 保解码核干净。仍不够则双解码线程双帧交替 (banks=4)。
9. [顺手] `COMP_LEN_MAX` 校验、SO_RCVBUF 调大到 512 KB (5G 突发), `listen(lfd,1)` 与 ghost guard 逻辑不动。

## 4. PC 端

### 4.1 预渲染循环推 vs 实时渲染: 没有悬念

现渲 0.6–2.5 s/帧, 距 38.5 ms 差 **16–65 倍**, numpy 管线不可能实时化 (那是 GPU 改写, 另立项)。26 fps 的运行模型只能是 **预渲染 + 循环推流** (`render` → `stream --dir --loop`), 与现工作流一致。26 fps 下体验换算: 72 帧循环 = 2.77 s 一循环 (现 4.5 fps 下同素材 16 s), 动画帧数建议按新页率重烘 (如 dance 类 104 帧 = 4 s 循环)。

### 4.2 但 stream 循环本身也要提速: 预压缩缓存

现 `stream --dir` 每次发送都重读 4.4 MB .bin + 实时 zlib-6 (**x86 实测 41 ms/帧 > 38.5 ms 预算**, WSL 单核还会抖) —— 循环推 26 fps 会被 PC 压缩卡住。改法:

- `render` 结束时 (或 `stream` 首个循环时) 生成 **压缩缓存** `frame_XXXX.pvz` (= 线上 payload 原样 + 16 B 头), delta 模式则 `frame_XXXX.pvd` (对前一帧的 XOR+zlib, 环形: 最后一帧的 delta 参考第一帧关键帧)。
- `stream` 启动时把整循环载入内存 (72 帧 × ~110 KB ≈ 8 MB, 可忽略), 推流热路径变成 **纯 `sendall` + 等 ACK, PC CPU ≈ 0**, 节拍完全由板端 ACK 决定。
- `--fps` 语义不变: 设 30 (> 26) 让 ACK 门控自动贴住翻页率, 与现在 "设高贴脸" 的经验一致。

### 4.3 POV Studio 新控件

| 控件 | 说明 |
|---|---|
| fps 上限 | Spinbox 上限 30→**32**, 预设档 "双屏 26"; 状态栏并排显示 目标/实际页率, 差 >10% 变红 |
| 链路占用表 | wire Mbps / 链路估值 (2.4G=28, 5G=75, 有线=300) 百分比条; 超 70% 黄, 90% 红 |
| delta 开关 + 关键帧周期 | 默认开, K=52; 检测到首帧 NAK 自动降级全帧并在 UI 标注"板端旧版" |
| 抖动模式 | "时域抖动 (画质) / 冻结相位 (delta 省带宽)" 二选一, 关联提示预计帧大小 |
| 渲染片数 | 360 / 180 选择, 180 时提示"外缘角向分辨率减半, 线上体积约 -45%" |
| 预压缩缓存 | 渲染后自动生成 .pvz 勾选 (默认开); 缓存命中时 stream 面板显示 "cached" |
| 板端统计回显 | 复用现有"板日志"按钮, 抓 pov_rxd 每秒统计行, 显示 解码 ms / 丢帧 / 错过窗口 |

### 4.4 ACK 门控在 26 fps 下的余量说明

解耦后 (板端 §3.3) ACK 周期 = 板端解码周期。stop-and-wait 每帧引入 1×RTT (5G ~3–5 ms, 占预算 ~10%), 暂不做发送窗口。若 S4 实测 RTT 抖动导致页率贴不住 26, 再加 "window=2" (发 N+1 不等 N 的 ACK, 协议无需改, 板端 recv 缓冲天然吸收) —— 有明确触发条件才做。

## 附: 一页结论

- 带宽: **5G 锁频为主 (0 代码, 占用 11–18%) + delta 做保险 + 180 片做画质旋钮 + GbE 保底**; 2.4G 只作 delta+180 的降级模式。
- 协议: PVS1 头不动, **只加 flags bit2=DELTA**; 关键帧是发送端策略, 双屏相位是 PL 配置, 都不进协议。
- 板端: 真瓶颈在 CPU 不在网 —— 串行路径 130–230 ms/帧 (SO 拷贝 37–73 ms + inflate 30–90 ms 两大头), 必改 = 三缓冲双线程 (ACK 与翻页解耦) + WC 映射 + 半圈双窗口翻页 + 去 crc32; inflate 实测 (S0) 决定是否动用 zlib-ng/zstd/180 片后手。
- PC 端: 预渲染循环推 + **预压缩缓存** (否则 zlib-6 的 41 ms/帧 先把 PC 卡死), Studio 加页率/链路占用/delta/片数四组控件。
