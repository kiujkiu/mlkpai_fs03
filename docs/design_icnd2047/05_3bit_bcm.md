## 1. 为什么能做：OE 窗口"免费"的真实边界

> ⚠ **原写**："`oe ≤ 111` 时行周期恒 195 拍 ⇒ BCM 三个权重取 **27/54/108** 沿 (1:2:4)，
> 全部 ≤111，**全部免费**。"
> **已被 2026-08-20 上板实测推翻**：111 这道门槛**只管行内最后一个 plane**。
> 按 ≤111 去凑 1:2:4，白白把最大权重压到了 108，亮度损失 43% 全是这么来的 (§5)。

### 1.1 111 这个数是怎么来的

LWAIT 的退出条件是

```
disp_ready = oe_done && adv_fired && !rd_busy && !row_go_r   // icnd2047_panel_core.v:242
```

它同时等**两件事**：

- (a) 上一个显示窗收完 —— `oe_done`
- (b) 行驱把行选推进完 —— `rd_busy` 落 (`row_drv_icnd1028`，约 80 拍)

1-bit 时每行都要做 (b)，和 192 拍移位窗一叠加，OE 一旦超过 111 就开始撞 (b)
⇒ 经验式 `LWAIT = max(0, oe−111)`。**111 不是 RTL 里的字面常量**，是这两件事叠出来的。

### 1.2 plane 边界**不是**行边界 ⇒ (b) 根本不发生

`icnd2047_panel_core.v:466-474`：plane<2 时 `shift_row` 不动、`adv_fired` **保持 1**
⇒ P2 藏尾推进不会再发 `row_go` ⇒ 行驱一步不走，`rd_busy` 恒 0。
**行驱只在 plane2 之后走一次。**

⇒ plane0 / plane1 只需要等 (a)，而 (a) 完全藏在下一 plane 的 194 拍
(FETCH 1 + LOAD 1 + SHIFT 192) 里。

### 1.3 【实测】三个 plane 的 OE 上限不一样

写 `0x0C` sub01 / sub10 改权重，读 `R 0x28` `frame_period`（纯 PL 拍数）：

| 配置 | `frame_period` | 判读 |
|---|---|---|
| w0=111 w1=54 w2=108 | 31590 | 基准 |
| w0=111 **w1=187** w2=108 | 31590 | plane1 拉满 **免费** |
| **w0=187** w1=54 w2=108 | 31590 | plane0 拉满 **免费** |
| w0=111 w1=54 **w2=187** | **35694** | = 31590 + 54×(187−111) = 31590 + 54×76 ✅ |

| plane | OE 上限 | 为什么 |
|---|---|---|
| plane0 | **187** (RTL 箝位先撞上；结构上限 ≈194) | 不推行驱，只藏在移位窗里 |
| plane1 | **187** (同上) | 同上 |
| plane2 | **111** | 它是行边界，要等行驱那 80 拍 |

⇒ 🎯 **最大权重必须放在不受限的 plane0** ⇒ host 侧 **plane0 装 MSB**。
权重取 **184 / 92 / 46**（精确 4:2:1）。

**为什么是 184 不是 192**：RTL 把 OE 箝在 `[2,187]`
(`icnd2047_panel_core.v:139-141`)，而 4:2:1 要求最大权重是 4 的倍数
⇒ 4×46=184 ≤187，4×47=188 >187。**箝位 187 才是那个真正的绑定约束，不是 192。**

## 2. 🔴 必须是**行内** BCM，不能是屏级

屏级 BCM (扫完整屏 plane0，再整屏 plane1…) 在 POV 上是错的：
三遍之间转子转过 `3 × 421µs × 15rps × 360° = 6.8°`，
三个位平面落在**三个不同角度**上 ⇒ 颜色沿角度方向分离拖尾。

**行内 BCM**：每行连续发 plane0/1/2 再进下一行。
同一像素的三个位平面在 `3 × 195 拍 = 585 拍 = 23.4 µs` 内完成
⇒ 角度差 **0.13°**【推算，用 §3.2 的 aclk=25 MHz】，可忽略。

```
行 r: [移位 plane0 192bit][OE 184 沿] [移位 plane1][OE 92] [移位 plane2][OE 46] → 行 r+1
                 ↑MSB                        ↑bit1              ↑LSB
```

已固化进 `stream/board/pov_boot.sh` 的 `CFG_MISC = 0x98366F01`
（现在由 `OE_W0` 算出来，`pov_boot.sh:70`；BPP3=0 时逐位仍是这个数）。

### 3.2 ✅ `aclk` 悬案已结案：**≈25 MHz**

> ⚠ **原写**（08-20 上午）："实测与硬件证据直接冲突，**未解**……在定案之前不要把任何一方当结论用。"
> **08-20 晚已定案**：`frame_period_o` 接到 `R 0x28` 之后，用**纯 PL 拍数 ÷ 墙钟秒数**
> 直接算频率，不依赖任何一方的假设 —— 这正是当初那节写的"定案方法"，照做了，结论是 **25 MHz**。

【实测】

| 配置 | `R 0x28` (PL 拍数) | 整屏率 (墙钟) | ⇒ aclk |
|---|---|---|---|
| 1-bit | 10530 | 2334.7 Hz | **24.58 MHz** |
| 3-bit | 31590 | 826.5 Hz | **26.11 MHz** |

两次**独立**测量都指向 25 MHz。6% 分散来自 `oeprobe` 采样漏沿，而这个误差是
**单向的**（漏沿 ⇒ 低估整屏率 ⇒ 低估 aclk），所以两个数都是下界，真值贴 25 更合理。

之前扫 `oe_window` 48/111/149/187 反算出的 **~40 ns/沿** 与此一致；
行周期通式 `195 + max(0, oe−111)` 四点全中 ⇒ **195 拍/行的 RTL 模型本身是对的**，
错的只是"一拍 = 20 ns"这个换算。

**已亲手排除的两个"测量侧"解释**（保留，因为这两条是结论能立住的前提）：

1. **不是 oeprobe 的时基错**：板上 `/proc/uptime`（`CLOCK_MONOTONIC` 同源）增量 20.05 s
   对 PC 墙钟 23.07 s（差额是 ssh 开销）。时基快/慢 2× 都会立刻暴露，没有。
2. **不是跑了别的 bit**：SD 卡 live `BOOT.bin` md5 `2678fe69…` 与本地
   `stream/boot/BOOT.bin` **逐位相同**。

### 3.2.1 🔴【未决】那五条硬件证据里必有一条是错的

结论定了，**但矛盾还没消**。下面五条独立证据全部指向 50 MHz，**至今没找到是哪条错**：

| 证据 | 出处 |
|---|---|
| BD 里 `ps7_0_FCLK_CLK0` **直连** `panel_0/s_axi_aclk`，全 BD 只有 5 个 cell，无 `clk_wiz` | `build_panel/.../system.bd` |
| 实现后 `BUFGCTRL 1 / BUFH 0 / BUFR 0 / MMCM 0 / PLL 0`，单时钟域，constraint **20.000 ns** | `impl_1/..._clock_utilization_routed.rpt` |
| 时序约束 Clock Summary 只有 `clk_fpga_0 period 20.000 freq 50.000` | `impl_1/..._timing_summary_routed.rpt` |
| `ps7_init` 写 `0xF8000170 = 0x00400500` = 1000/5/4 = 50 MHz；与 100 MHz 老工程的 `0x00200500` 互为校验 | `mlkpai_panel.xsa` |
| RTL 里所有时序块都是 `posedge s_axi_aclk`，三个历史版本逐字相同，从来没有过 /2 | `pov_dual_top.v` |

⇒【推算】`fast` 的实际线速率是 **25 Mbps 而非设计注释写的 50 Mbps —— 设计目标从未跑到过**。
某处存在一级还没找到的 /2（或某条证据读错了）。**查明并去掉它，3-bit 的角分辨率直接翻倍**（§3.3 末行）。

⚠ 在找到那一级之前：**不要**据此去改 XDC / 提频 / 改约束。`R 0x28` 是目前唯一不含频率假设的量具，
任何新的时间结论都应该先过它。

### 3.3 3-bit 的时间代价 = 精确 3.00×【实测】

行周期 = FETCH(1) + LOAD(1) + 192 移位 + LWAIT(0) + DISP(1) = 195 拍。
行内 BCM 三个 plane 各走一遍完整行周期 ⇒ **585 拍/行**，与 aclk 频率无关。
`R 0x28` 实测 10530 → 31590 = **精确 3.00×**，且运行时可来回切。

| 配置 | 行周期 | 整屏 | 15 rps 每圈角度 | 角分辨率 |
|---|---|---|---|---|
| 1-bit slow (08-20 之前) | 15.52 µs | 838 µs | 80 | 4.5° |
| **1-bit fast (现在)** | **7.81 µs** | **421 µs** (10530 拍) | **158** | **2.3°** |
| **3-bit fast (现在)** | **23.4 µs** | **1264 µs** (31590 拍) | **53** | **6.8°** |
| (若 §3.2.1 的 /2 被拔掉) 3-bit @50M | 11.7 µs | 632 µs | 105 | 3.4° |

拍数是【实测】，µs 和角度数是【推算】(拍数 ÷ 25 MHz)。
⇒ 现状下 3-bit 可用，每圈 **53 个角度**（这就是槽数取 50 的由来，§4）。

## 4. 带宽账 — 反直觉：载荷**降低**

> ⚠ **原写**：槽数 60，双面 4.42 MB。**08-20 改为 50** ——
> 3-bit 整屏 1264 µs @15 rps 只够 53 个角度 (§3.3)，取 50 留余量。
> `pov_boot.sh:32` 已改成 50。方向没错，只是数变了。

每片 3× 数据，但槽数从 360 降到 50 (匹配面板真实能力，见记忆
`project_pov3d_nslices_match_panel`)：

| | 片/双面 | B/片 | 双面帧长 |
|---|---|---|---|
| 今天 (1-bit, 360 槽/面) | 720 | 12288 | **8.85 MB** |
| **3-bit, 50 槽/面** | 100 | 36864 | **3.69 MB** = **÷2.4** |
| (参考) 1-bit, 90 槽 | 180 | 12288 | 2.21 MB |

⇒ 相对**今天在跑的配置**，3-bit 让载荷降到 42%，`dec`/`cpy`/链路全部同比下降。
相对"1-bit + 槽数优化"的理想态，3-bit 是 1.7× 载荷 —— 这才是它的真实代价。

## 5. 亮度账 — 全白 **−3.3%**，几乎无损

> 🔴 ⚠ **原写**："3-bit 全白亮度 **−43%**（占空 0.3231 vs 1-bit 0.5692）……
> LED 平均电流下降在这里是副作用为正。"
> **已被 2026-08-20 上板实测推翻。** 错误前提是"三个 plane 都受 `oe ≤ 111` 限制"(§1)。
> 实际只有 plane2 受限 ⇒ 把 4W 放到 plane0 就把这 43% 拿回来了。
> 原来那句"电流下降是副作用为正"也跟着作废 —— 现在电流回到 1-bit 水平，
> **5V 轨余量按 1-bit 那本账算**。

| 配置 | 点亮沿 / 行周期 | 占空 | 相对 1-bit |
|---|---|---|---|
| 1-bit @ oe=111 | 111 / 195 | 0.5692 | 100% |
| **3-bit @ 184/92/46 (plane0=MSB)** | 322 / 585 | **0.5504**【实测 oeprobe 0.549/0.550】 | **96.7%** |
| ~~3-bit @ 27/54/108 (plane0=LSB)~~ | 189 / 585 | 0.3231 | 56.8% ← 已作废 |

且 `frame_period` **一拍不涨**（31590 恒定）⇒ **亮度是白拿的，不花时间**。

【推算】理论天花板是 192/96/48 = 336/585 = 0.5744（比 1-bit 还亮一点点），
但要动 RTL 的 `[2,187]` 箝位才拿得到，收益只有 +4%，不值。

### 5.1 🔴 位序与权重**必须成对改**

- host 侧 `pack_obs.pack_slice`：plane p 装 `bit(2−p)` ⇒ **plane0=MSB / plane1=bit1 / plane2=LSB**
- 硬件权重：`oe_w0=184 / oe_w1=92 / oe_w2=46`

⚠ **只改一个就是坏的**：旧的 27/54/108 配上 MSB-first，码值 1 (LSB 落 plane2，108 沿)
会比码值 2 (bit1 落 plane1，54 沿) **还亮** —— **08-20 上板复现过这个非单调**。
而且因为 `pov_rxd` 每 `BCM_REASSERT_EVERY = 256` 次 apply 会强制重写一遍寄存器
(`pov_rxd.c:282`)，如果引导脚本和守护进程给的权重不一致，现象还会**周期性飘忽**，
比稳定错更难查。

⇒ 改权重前先读本节；`pack_obs.py:19-40` 和 `pov_rxd.c:265-277` 两处注释互为交叉引用。

若还要压亮度或修 gamma，走 host 侧 `pack_obs --led-gamma`，**别动 `oe_w*` 的比例**。

## 8. `le_plane_mode` 与"边界糊"：两个方向都试过，都不是它

## 9. 已知风险

- 🔴 `bit29` 翻 fast 的 SI 未在 trans_v12 引脚序上验证过（仓库无记录）。
  SI 是数据完整性问题，FPGA 侧无回读通路 ⇒ 只能靠屏面目视
- 🔴 三个位平面的**电流阶跃**比 1-bit 密 3 倍：`q_gap` 行边界静默区在 FSM 里挂在
  **每个 plane 的行周期**上，所以 plane 边界也照插死区 —— 密度翻 3 倍，
  可能要重调（2026-07-17 行边界串扰案的同一机制）
- ⚠ 角分辨率 158 → 53 是真实降质（1-bit fast 对 3-bit fast），需实拍确认可接受。
  ~~"89 → 59"~~ 是旧基线下的数，已作废
- ⚠ 8 级灰度在 1-bit Bayer 之上是**减少**抖动噪声，但量化跳阶可能更显眼
- ⚠ `bpp_mode=1` 时 AXI 的 fb 窗只有 9 bit `{row,word}`，够不着 plane 字段 ⇒
  **只能改 plane0**，完整 3-bit 内容必须走 DDR 取帧 (`pov_dual_top.v:545-547`)

按"还得花多少功夫"排，不是按重要性：

1. 🔴 **`aclk` 那五条硬件证据里哪一条是错的** (§3.2.1)。结论已定在 25 MHz，
   但机制没找到。找到它 ⇒ 3-bit 每圈角度 53 → 105，色深等于白拿

   3-bit 上板到现在一次都没读过
4. ⚠ **取帧时间预算翻 3 倍的影响**【推算，未实测】：每片取帧字节数 ×3
   (0x3000 → 0x9000)，但单片时间预算随槽数 360 → 50 变宽 7.2×

   要靠上一条的 `pair_miss` 来证

6. ⚠ **转动状态下的颜色分离**和**端到端 flip 帧率**都还没测 (§7 第 7/8 项)
