# 3-bit 色深 (每通道) — 行内 BCM 方案

分支 `feature/3bit-color`，2026-08-20 起。目标：每通道 1-bit → **3-bit**
(每像素 9 bit = 512 色)，且**不牺牲体积帧率**。

## 0. 现状基线 (实测，非推算)

| 项 | 值 | 出处 |
|---|---|---|
| 色深 | 每通道 1-bit，每像素 8 色 | `tools/pack_obs.py` |
| 观察者图 | `H=180, W=160, 3` | `pack_obs.pack_slice` |
| fb 布局 | 9 lane × 512 × 32b，addr={row[5:0],pair[2:0]} | `panel_engine_2047.v:g_fb` |
| 实占 | 54 行 × 6 pair = **324 / 512** | 同上 |
| 行周期 | 195 拍 (1 取指 + 1 装载 + 192 移位 + LWAIT + 1 显示) | `icnd2047_panel_core.v` |
| `LWAIT` | `max(0, oe_window − 111)` | 仿真三点吻合 |
| 2D 刷新 | **实测 1335 Hz = 749 µs/屏** (ddr_slow=1 降级态) | 08-10 `oeprobe.c` |
| PL 占用 | LUT **5.08%** / BRAM **18 RAMB18 = 9 tile (6.4%)** | `impl_1` utilization |

## 1. 为什么能做：OE 窗口 ≤111 沿是免费的

`oe ≤ 111` 时行周期恒 195 拍 —— OE 显示窗**完全藏在下一行的 192 拍移位里**
(ICND2047 内置双缓存 = 架构固有 overlap)。超过 111 才插 LWAIT。

⇒ BCM 的三个权重位取 **27 / 54 / 108 沿** (比例 1:2:4)，**全部 ≤ 111，全部免费**。
时间代价只来自"每行要移位 3 次"，不来自 OE 加长。

## 2. 🔴 必须是**行内** BCM，不能是屏级

屏级 BCM (扫完整屏 plane0，再整屏 plane1…) 在 POV 上是错的：
三遍之间转子转过 `3 × 749µs × 15rps × 360° = 12.1°`，
三个位平面落在**三个不同角度**上 ⇒ 颜色沿角度方向分离拖尾。

**行内 BCM**：每行连续发 plane0/1/2 再进下一行。
同一像素的三个位平面在 `3 × 195 拍 = 11.7 µs` 内完成 ⇒ 角度差 **0.063°**，可忽略。

```
行 r: [移位 plane0 192bit][OE 27 沿] [移位 plane1][OE 54] [移位 plane2][OE 108] → 行 r+1
```

## 3. 时间账 (2026-08-20 上板实测锚定)

### 3.1 `bit29` 翻 fast — 已验证 ✅

| | slow (翻前) | **fast (翻后)** | 比值 |
|---|---|---|---|
| `status[7] ddr_slow` | 1 | **0** | — |
| OE 沿数 / 2s | 258,649 | **536,277** | 2.07× |
| 行周期 | 15.52 µs | **7.81 µs** | ÷2.07 |
| 整屏 (54 行) | 838 µs | **421 µs** | ÷2.07 |
| 2D 刷新 | 1193 Hz | **2373 Hz** | 2.07× |
| OE-low 占空 | 0.574 | **0.569** | 守恒 ✅ |

已固化进 `stream/board/pov_boot.sh` 的 `CFG_MISC = 0x98366F01`。

### 3.2 🔴 `aclk` 频率：实测与硬件证据直接冲突，**未解**

⚠ **先前版本在这里写"aclk = 25 MHz，悬案结案"—— 那个结论下早了，现已撤回。**

`oe_window` 扫 48/111/149/187，用 `duty × 行周期 ÷ oe` 反算单沿时长：

| oe | 行周期 | duty | ns / 沿 |
|---|---|---|---|
| 48 | 8.05 µs | 0.245 | 41.1 |
| 111 | 7.81 µs | 0.569 | 40.0 |
| 149 | 9.02 µs | 0.639 | 38.7 |
| 187 | 11.13 µs | 0.690 | 41.1 |

四点一致落在 **~40 ns/沿**。fast 模式 1 沿 = 1 aclk 拍 ⇒ 指向 **aclk ≈ 25 MHz**。
行周期通式 `195 + max(0, oe−111)` 四点全中，所以 **195 拍/行的 RTL 模型本身是对的**。

**但硬件侧五条独立证据全部指向 50 MHz**：

| 证据 | 出处 |
|---|---|
| BD 里 `ps7_0_FCLK_CLK0` **直连** `panel_0/s_axi_aclk`，全 BD 只有 5 个 cell，无 `clk_wiz` | `build_panel/.../system.bd` |
| 实现后 `BUFGCTRL 1 / BUFH 0 / BUFR 0 / MMCM 0 / PLL 0`，单时钟域，constraint **20.000 ns** | `impl_1/..._clock_utilization_routed.rpt` |
| 时序约束 Clock Summary 只有 `clk_fpga_0 period 20.000 freq 50.000` | `impl_1/..._timing_summary_routed.rpt` |
| `ps7_init` 写 `0xF8000170 = 0x00400500` = 1000/5/4 = 50 MHz；与 100 MHz 老工程的 `0x00200500` 互为校验 | `mlkpai_panel.xsa` |
| RTL 里所有时序块都是 `posedge s_axi_aclk`，三个历史版本逐字相同，从来没有过 /2 | `pov_dual_top.v` |

**我另外亲手排除了两个最可能的"测量侧"解释**：

1. **不是 oeprobe 的时基错**：板上 `/proc/uptime`（`CLOCK_MONOTONIC` 同源）增量 20.05 s
   对 PC 墙钟 23.07 s（差额是 ssh 开销）。时基快/慢 2× 都会立刻暴露，没有。
2. **不是跑了别的 bit**：SD 卡 live `BOOT.bin` md5 `2678fe69…` 与本地
   `stream/boot/BOOT.bin` **逐位相同** —— 就是上表那个 BD 出来的。

⇒ 两组证据互相排斥，且不存在"中间解"（FSM 层面的拖慢会压低占空比，而占空比四点精确吻合）。
**在定案之前，不要把任何一方当结论用。**

### 🎯 定案方法：读 `frame_period` (R 0x28)

`icnd2047_panel_core` 有 `frame_period_o` = "最近一整屏走了多少个 aclk 拍"，
但 `panel_engine_2047.v` 目前 `.frame_period_o ()` 悬空，`pov_dual_top.v` 的
`R 0x28` 也特意留空等着它。**接上这条线，矛盾当场可判**：

```
aclk_Hz = frame_period(纯 PL 拍数) / 整屏墙钟秒数(oeprobe, CPU 时基已验证正确)
```

不依赖任何一方的假设。这个寄存器当初加进设计就是为了"免示波器测刷新率"。
（已交给 RTL agent 实现，随三平面改造一起上板。）

### 3.3 3-bit 的时间代价 = 精确 3.00×

行周期 = FETCH(1) + LOAD(1) + 192 移位 + LWAIT(0) + DISP(1) = 195 拍。
行内 BCM 三个 plane 各走一遍完整行周期 ⇒ **585 拍**，与 aclk 频率无关。

| 配置 | 行周期 | 整屏 | 15 rps 每圈角度 | 角分辨率 |
|---|---|---|---|---|
| 1-bit slow (08-20 之前) | 15.52 µs | 838 µs | 80 | 4.5° |
| **1-bit fast (现在)** | **7.81 µs** | **421 µs** | **158** | **2.3°** |
| **3-bit fast** | **23.4 µs** | **1264 µs** | **53** | **6.8°** |
| 3-bit fast + aclk 50M | 11.7 µs | 632 µs | **105** | 3.4° |

⇒ 现状下 3-bit 可用，角分辨率 53 个角度 (6.8°)。
⇒ 若 §9 的 aclk 问题能解，3-bit 反而比今天的 1-bit 还细 (105 vs 80)。

## 4. 带宽账 — 反直觉：载荷**降低**

每片 3× 数据，但槽数从 360 降到 60 (匹配面板真实能力，见 `project_pov3d_nslices_match_panel`)：

| | 片/面 | B/片 | 双面帧长 |
|---|---|---|---|
| 今天 (1-bit, 360 槽) | 360 | 12288 | **8.85 MB** |
| **3-bit, 60 槽** | 60 | 36864 | **4.42 MB** = ÷2.0 |
| (参考) 1-bit, 90 槽 | 90 | 12288 | 2.21 MB |

⇒ 相对**今天在跑的配置**，3-bit 让载荷减半，`dec`/`cpy`/链路全部同比下降。
相对"1-bit + 槽数优化"的理想态，3-bit 是 2× 载荷 —— 这才是它的真实代价。

## 5. 亮度账 — 全白 −43%

| | 点亮沿 / 行周期 | 占空 |
|---|---|---|
| 1-bit @ oe=111 | 111 / 195 | 56.9% |
| 3-bit @ 27+54+108 | 189 / 585 | 32.3% |

全白亮度降到 **56.8%**。考虑到 5V 轨余量本就紧张 (双屏 + dongle 峰值)，
LED 平均电流下降在这里是**副作用为正**。若需补回，可在 host 侧做 gamma 编码，
把常用色阶推向高位平面。

## 6. 改动清单

### RTL (`icnd2047_panel_core.v` / `panel_engine_2047.v`)
1. fb 深度 512 → **1024**，addr = `{row[5:0], plane[1:0], pair[2:0]}` (972/1024)
   BRAM: 18 RAMB18 → 18 RAMB36 (9 tile → 18 tile，**6.4% → 12.9%**，140 tile 里毫无压力)
2. 核内加 `plane[1:0]` 计数器，在**行循环内层**：`EG_DISP` 后若 `plane<2` 则
   `plane++` 且**不推进 `shift_row`**，回 `EG_FETCH`；`plane==2` 才进下一行
3. `win_aclk` 按 plane 选权重：三个 8-bit 寄存器 `oe_w0/w1/w2`
   (默认 27/54/108)，沿用现有 `[2,187]` 箝位
4. `frame_period_o` 统计维持"整屏"语义 (现在是 31590 拍)

### 寄存器 (`0x0C` sub10 已满，需新 subcmd)
- 新增 `oe_w1/oe_w2` (`oe_w0` 复用现有 `oe_window[15:8]`)
- 新增 `bpp_mode` 位：0=1-bit (兼容旧内容)，1=3-bit
  ⚠ 必须可运行时切换，否则旧的 1-bit 内容和空闲动画全废

### Host (`tools/pack_obs.py` / `stream/pc/povstream.py`)
- `SLICE_STRIDE` 0x3000 → **0x9000** (三个 plane 顺序排列，每 plane 沿用现布局)
- `pack_slice` 输入从 bool 图改 `uint8` 0..7 三通道，按位切成 3 个平面
- Bayer 抖动从"1-bit 阈值"改成 **8 级量化 + 残差抖动** (误差扩散或有序抖动)
- `--n-slices 60` 走已做好的槽数参数

### 板端 (`pov_rxd.c`)
- 帧长校验：`n_slices × SLICE_STRIDE`，stride 从头里推而不是常量
- `PVS_FLAG_3BIT`，与 `PVS_FLAG_FOLD_A`/`DUAL_FACE` 正交
- ⚠ 双面路径 `:1391` 那两个写死的 `PVS_N_SLICES` 必须一起改 (见 nslices 记忆)

### 冷启动 (`pov_boot.sh`)
- 默认内容、`oe_w*`、`bpp_mode` 一并固化，否则重启回 1-bit

## 8. 已知风险

- 🔴 `bit29` 翻 fast 的 SI 未在 trans_v12 引脚序上验证过 (仓库无记录)
- 🔴 三个位平面的**电流阶跃**比 1-bit 密 3 倍，行边界静默区 `q_gap` 可能要重调
  (2026-07-17 行边界串扰案的同一机制)
- ⚠ 角分辨率 89 → 59 是真实降质，需实拍确认可接受
- ⚠ 8 级灰度在 1-bit Bayer 之上是**减少**抖动噪声，但量化跳阶可能更显眼

## 9. ⏸ 待定案：aclk 到底是 25 还是 50 MHz

取决于 §3.2 的定案结果，两种走向完全不同：

- **若实测对（25 MHz）**：说明有一级还没找到的 /2，`fast` 的实际线速率是 25 Mbps
  而非设计注释写的 50 Mbps —— 设计目标从来没跑到过。查明并去掉那一级，
  3-bit 每圈角度从 53 涨到 105，比今天的 1-bit（80）还细，色深等于白拿。
- **若硬件证据对（50 MHz）**：面板本来就在 4746 Hz，`oeprobe` 的绝对刻度要修，
  本文档所有"实测"绝对时间都要除以 2（比值和占空比不受影响），
  §3.3 的角度数要翻倍重算。

⚠ 两种走向都**不改变 3-bit 的 3.00× 结构性代价**，也不改变 §4 的带宽账
（那本账只跟槽数和字节数有关）。所以 3-bit 的实现工作不必等这个结论，
但**上板前必须定案**，否则槽数（60 还是 105）会选错。

### 如果最终要提 FCLK0 50 → 100 MHz（独立议题）

- 改 `vivado/create_panel_proj_v6.tcl:60` 的 `PCW_FPGA0_PERIPHERAL_FREQMHZ`
- 要重跑：BD → 综合 → 实现 → 重导 XSA → **重建 FSBL**（ps7_init 才是真正写
  `0xF8000170` 的地方）→ 重打 `BOOT.BIN` → 冷启动
- 🔴 **时序上会挂**：最差 setup 路径 data path delay **11.987 ns**
  （logic 0.58 / route 11.41），slack 6.888 @ 20 ns ⇒ **fmax ≈ 76 MHz**。
  最差路径的源是复位大扇出网 `rst_ps7_0_50M/… → u_core/g_oddr_sdi[2]/R`，
  95% 是布线 ⇒ 复位打拍/复制是第一件该做的事
- 🔴 **hold 余量只有 0.036 ns**，任何重新布局布线都可能翻车，重建后必须盯 WHS
- 🔴 **XDC 里一条 `create_clock` / `set_output_delay` 都没有** —— SDI/DCLK/LE/OE 的
  ODDR→pad 路径**从来没被工具分析过**（时序报告 Unconstrained Path Table 明写
  `clk_fpga_0 → (none)`）。提频等于没有任何工具侧安全网，应先补虚拟时钟 + 输出约束
